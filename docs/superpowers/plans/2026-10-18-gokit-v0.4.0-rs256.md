# gokit v0.4.0 — RS256 auth + revocation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Release gokit v0.4.0 with RS256 token signing/verification, Redis-backed token revocation and an RS256 HTTP auth middleware, on top of a v0.3.0 that builds and tests clean.

**Architecture:** All additions are new files or new fields; existing HS256 APIs (`auth.GenerateToken`, `auth.ValidateToken`, `middleware.JWTAuth`) are untouched. `auth` gains key loading, `RSASigner`, `RSAVerifier`, `RevocationChecker` and `RedisRevocationStore`. `middleware` gains `RS256Auth`/`OptionalRS256Auth`. `config.Base` gains an `Auth` block.

**Tech Stack:** Go 1.26 (`go 1.26.0` in go.mod), `github.com/golang-jwt/jwt/v5`, `github.com/google/uuid` (already in go.sum), `github.com/redis/go-redis/v9`, `github.com/alicebob/miniredis/v2` for tests, testify.

**Spec:** `~/GitHub/go-project/docs/superpowers/specs/2026-10-18-go-project-design.md`, Part 1.

## Global Constraints

- Repo `~/GitHub/gokit`, branch `feat/v0.4.0-rs256` from `master` (= tag v0.3.0, 6008f18).
- Module path `github.com/piresc/gokit`; no change to `go 1.26.0`.
- Do not change signatures or behavior of `auth.GenerateToken`, `auth.ValidateToken`, `middleware.JWTAuth`, `middleware.GetUserID`, `middleware.GetRole`, `middleware.RequireRole`.
- No Gin imports. `net/http` only.
- Error bodies use the existing `response.Error(w, status, msg)` envelope `{"status":"error","error":"<msg>"}`.
- Revocation key format: `revoked:<jti>`.
- Redis failure during a revocation check: default fail-closed → `503`, header `Retry-After: 5`, body message `service unavailable`; option `FailOpen: true` → allow and log a warning.
- Status codes: missing/malformed header, bad signature, non-RSA alg → 401 `authentication required`; expired → 401 `token expired`; revoked → 401 `token revoked`.
- Env var names: `JWT_PRIVATE_KEY_PEM`, `JWT_PRIVATE_KEY_PATH`, `JWT_PUBLIC_KEY_PEM`, `JWT_PUBLIC_KEY_PATH`, `ACCESS_TOKEN_TTL` (default `15m`), `REFRESH_TOKEN_TTL` (default `720h`), `JWT_ISSUER`.
- Every task ends with `go build ./... && go vet ./... && gofmt -l .` clean (gofmt prints nothing) for the packages it touched.

## Review Focus

- PEM supplied through an env var with literal `\n` sequences (how Coolify/Docker pass multi-line values) must load — test in Task 2.
- A token signed HS256 with the public key bytes as the HMAC secret (alg-confusion) must be rejected as 401 — test in Task 2 and Task 4.
- A token with an empty `jti` must skip the revocation lookup, not query `revoked:` — test in Task 4.
- Redis hanging (not just refusing) must produce 503 within `RevocationTimeout` (default 1s), well under nginx's 5s — test in Task 4 with a blocking fake checker.
- A config file without any `auth:` block must still load (services that don't use RS256) and must not require `JWT_SECRET` — test in Task 5.

### Task 2: RSA keys, signer, verifier

**Files:**
- Create: `auth/rsa.go`, `auth/rsa_test.go`

**Interfaces:**
- Produces (package `auth`):
  - `func LoadRSAPrivateKey(pemValue, path string) (*rsa.PrivateKey, error)` — if `pemValue` (after replacing literal `\n` with newline and trimming) is non-empty use it, else read `path`; both empty → error `auth: no RSA private key configured`. Accept PKCS#1 and PKCS#8.
  - `func LoadRSAPublicKey(pemValue, path string) (*rsa.PublicKey, error)` — same precedence; PKIX. Error `auth: no RSA public key configured` when both empty.
  - `type RSAClaims struct { Email string \`json:"email"\`; Role string \`json:"role"\`; jwt.RegisteredClaims }` — `Subject` = user ID, `ID` = jti.
  - `type RSASigner struct` ; `func NewRSASigner(key *rsa.PrivateKey, issuer string, ttl time.Duration) *RSASigner`
  - `func (s *RSASigner) Sign(userID, email, role string) (token, jti string, expiresAt time.Time, err error)` — RS256, jti = `uuid.NewString()`, sets iss/sub/jti/iat/exp.
  - `type RSAVerifier struct` ; `func NewRSAVerifier(key *rsa.PublicKey) *RSAVerifier`
  - `func (v *RSAVerifier) Verify(token string) (*RSAClaims, error)` — parse with `jwt.WithValidMethods([]string{"RS256"})` and `jwt.WithExpirationRequired()`; empty `sub` → invalid; returns `ErrTokenExpired` for expiry, `ErrTokenInvalid` for everything else (wrap the cause with `%w` only under these sentinels). A verified token therefore always has non-nil `ExpiresAt` and non-empty `Subject`.
  - `var ErrTokenExpired = errors.New("auth: token expired")`, `var ErrTokenInvalid = errors.New("auth: token invalid")`
- Produces (package `testkit`): `func NewRSAKeyPair(t testing.TB) (priv *rsa.PrivateKey, privPEM, pubPEM []byte)` — 2048-bit, PKCS#1 private PEM, PKIX public PEM.

### Task 4: RS256 HTTP middleware

**Files:**
- Create: `middleware/rs256.go`, `middleware/rs256_test.go`
- Modify: `middleware/auth.go` (add `KeyClaims` constant next to `KeyUserID`/`KeyRole`)

**Interfaces:**
- Consumes: `auth.RSAVerifier`, `auth.RSAClaims`, `auth.ErrTokenExpired`, `auth.RevocationChecker` (Tasks 2–3).
- Produces (package `middleware`):
  - `type RS256Options struct { Revocation auth.RevocationChecker /* nil = no revocation check */; FailOpen bool; RevocationTimeout time.Duration /* 0 → 1s */ }` — `IsRevoked` runs under `context.WithTimeout(r.Context(), RevocationTimeout)`, so a hung Redis yields 503 in ~1s (gokit's Redis client otherwise waits 3s × retries, past nginx's 5s proxy timeout).
  - `func (m *Middleware) RS256Auth(v *auth.RSAVerifier, opts RS256Options) func(http.Handler) http.Handler`
  - `func (m *Middleware) OptionalRS256Auth(v *auth.RSAVerifier, opts RS256Options) func(http.Handler) http.Handler` — no `Authorization` header → next with no claims; any present-but-bad header → same errors as `RS256Auth`.
  - `const KeyClaims contextKey = "claims"`; `func GetClaims(r *http.Request) (*auth.RSAClaims, bool)`
  - On success sets `KeyClaims`, `KeyUserID` (= `claims.Subject`), and `KeyRole` (if non-empty), so `GetUserID`, `GetRole`, `RequireRole` work unchanged.
  - Revocation errors are logged with `m.logger` (`Warn` when fail-open, `Error` when fail-closed) including the jti, never the token.
